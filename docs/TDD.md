# 1. What was built

A booking website where guests choose dates, see real prices with GST, and pay (test mode) in three steps; a staff admin for daily rates, website allotment, blackout dates and promo codes; one enquiry inbox for web, event-form, forwarded-email and WhatsApp messages (the last two simulated) with an AI router that classifies, extracts, assigns an owner and drafts a reply; and a daily CSV booking export. The core slice from the brief (room pages with availability and price, booking with test payment, rate and allotment admin, enquiry inbox with AI routing, guest and reservations roles) works end to end on seeded sample data. The structured event form, GM alerts, promo codes, export, guest accounts and booking lookup are included as depth.

**Why it matters (from the brief):** about ₹1.05 crore a year at stake: ₹33.3 lakh from moving 15% of agency room nights to direct, plus ₹72 lakh from event enquiries lost to slow replies. The design maps to the three success measures: direct share 12% → 20%, median first reply under 30 minutes, zero website overbookings. The inbox shows the median first-reply time live.

# 3. Architecture and why

**Stack: MERN.** React 18 (Vite) single-page app; Node/Express API; MongoDB with Mongoose; JWT in an httpOnly cookie.

```
Browser (React SPA, code-split admin)
   │  JSON over HTTPS, same origin, httpOnly SameSite=Lax session cookie
Express API ── helmet, rate limits, zod validation, role middleware
   ├─ routes/public     rooms, availability, price, bookings, lookup
   ├─ routes/admin      inventory bulk edit, promos, bookings, CSV export, alerts
   ├─ routes/enquiries  web form, ingest (email/WhatsApp), inbox, re-route, reply
   ├─ lib/              dates, pricing+GST, inventory engine, payments(mock), csv  (pure, unit-tested)
   ├─ services/         availability, booking orchestration, enquiry router
   └─ ai/               rules engine, Claude wrapper, classifier, draft guard, owner assignment
MongoDB: users, roomtypes, rateplans, inventories, promocodes, bookings, enquiries, notifications, counters
```

**Key decisions**

* **One service, one origin.** Express serves the built React app. The session cookie is first-party, there is no CORS surface, and there is one thing to deploy for an ₹8 lakh, 7-week project.
* **Cookie sessions, not tokens in localStorage.** JavaScript cannot read the session, which limits damage from XSS. SameSite=Lax plus JSON-only endpoints mitigates CSRF.
* **MongoDB.** Documents fit bookings (a price snapshot belongs inside the booking) and enquiries (AI output, history and replies are naturally nested). The one place that needs relational care, stock, is handled by a single-document atomic update (section 5).
* **Pure logic in `lib/`.** Pricing, dates, the inventory engine and the CSV writer have no database or HTTP in them, so the important rules are unit-tested without infrastructure.
* **Speed on slow networks.** No web fonts (system stacks), vector photos of 4–10 KB each, route-level code splitting (guest bundle about 67 KB gzipped; staff screens load only for staff), aspect-ratio boxes so nothing jumps, lazy-loaded images, long-cache hashed assets, gzip.

| Collection | Key fields | Notes |
|-------|--------------------------|------------------------------------|

| `RoomType` | slug, name, kind (room/villa), units, maxAdults, maxGuests, photos[], amenities[] | Physical inventory. |

| `PromoCode` | code, percent/flat, value, maxDiscount, minNights, validTo, maxUses, used, active | Redeemed with an atomic counter. |
| `Booking` | code, idempotencyKey (unique), roomType, plan, dates, guest{name,email,phone}, pricing (full snapshot), promo, payment{status, last4}, consentAt, status, createdDay | Price snapshot means later rate edits never change a confirmed booking. No card number or CVC is stored. |
| `Enquiry` | ref (ENQ-4410…), channel, message, form, lane, owner, status, gmAlert, ai{category, confidence, source, summary, extracted, warnings, draft}, replies[], history[], firstReplyAt, consentAt | Lane is separate from ai.category so a human re-route keeps the AI's original reading for audit. |

Dates are plain `YYYY-MM-DD` strings in the property's calendar (IST). That avoids timezone drift and makes "nights between two dates" a simple range query.

# 5. The hard part: allotment control, so the site never overbooks

**Rule:** the website may sell at most `allotment − sold` units of a room type on any night, and never on a blacked-out night.

**Mechanism:** a hold is one atomic conditional update per night:

```
updateOne(
  { roomType, date, blackout: false, $expr: { $lte: [ { $add: ['$sold', qty] }, '$allotment' ] } },
  { $inc: { sold: qty } })           // success only if modifiedCount === 1
```

There is no read-then-write. If two guests race for the last unit, MongoDB serialises the updates on that document and exactly one succeeds. A multi-night stay holds night by night; if any night fails, the nights already held are released, and the guest sees "the last room was just taken".

**Booking sequence** (`services/booking.js`): validate and price on the server (never trusting client prices) → idempotency check → hold every night → claim promo atomically → charge (mock) → persist the booking. A failure at any step after the hold releases the nights and the promo. A required `Idempotency-Key` header, unique-indexed on the booking, means a double click or retry returns the same booking and never a second one.

**Admin safety:** allotment cannot exceed physical units, and a bulk change never lowers allotment below what is already sold (those nights are skipped and reported). Cancelling releases the nights.

**Tests** (`test/inventory.test.js`): 50 simultaneous bookings for 3 units yield exactly 3 successes; overlapping multi-night stays under concurrency never exceed allotment on any night; partial failure rolls back; blackout and missing nights cannot be held. The in-memory store used in the tests mirrors Mongo's atomic conditional update semantics.

# 6. Pricing and GST

`quoteStay()` computes, per room per night: plan price → promo discount spread proportionally before tax → GST slab chosen from what the guest pays that night (5% up to ₹7,500, otherwise 18%). Totals are shown as subtotal, discount, GST by rate and total, so a stay that crosses the threshold (a peak weekend) shows both 5% and 18% lines. Promo rules (minimum nights, validity, caps, redemption limit) are in `evaluatePromo()`; tests cover slab boundaries (₹7,500 and ₹7,501), breakfast add-ons, promo moving a night into the lower slab, multiple rooms and each promo rejection.

# 7. The AI part: classify, extract, assign, draft, and what happens when it is wrong

```
message ─► rules engine (always) ──┐
        └► Claude (if key set) ────┴► validate (zod) ─► cross-check ─► confidence
confidence ≥ 0.6 ?  lane = category  :  lane = Unsorted (GM)
lane ─► owner = least-loaded person in the lane's role  (room→reservations, wedding/offsite→sales, complaint/unsorted→GM)
room + dates ─► quote from the rate table ─► draft (token {{QUOTE}} filled by the server)
complaint (or any complaint signal) ─► GM notification
```

* **Classification and extraction:** category (room, wedding, offsite, complaint), dates, month hints, guests, adults/children, nights and budget (₹, lakh, crore). Indian formats are handled ("14-16 Nov", "₹3.5 lakh", "team of 45"). The rules engine alone passes the three sample enquiries (ENQ-4410 Wedding, ENQ-4411 Room, ENQ-4412 Corporate offsite) in tests.
* **Claude layer:** the enquiry is passed as delimited data with an instruction not to follow text inside it. Output must match a strict schema; extracted dates are re-validated and discarded if invalid or in the past.
* **When it is wrong or unsure**
  * Confidence below 0.6, or "other", goes to the **Unsorted lane that the GM owns**, with a plain-language warning in the UI.
  * If Claude and the rules engine disagree and the rules engine is confident, confidence is capped below the threshold, so disagreement forces human review.
  * Malformed or failed model output, or a timeout (12 s), falls back to the rules engine; the enquiry is never lost or delayed.
  * **Staff re-route in one click** (lane control in the detail pane); the draft is regenerated for the new lane, the change is logged in the enquiry history.
  * **Drafts are never sent automatically.** A person reads, edits and presses Send (simulated in this build).
  * **Prices in drafts come from the rate table.** The model may write prose and a `{{QUOTE}}` token only; the server fills it. A draft containing a currency amount is discarded and replaced by a template. Event and complaint drafts contain no prices.
  * **Complaints always alert the GM**, including weak signals that are too uncertain to leave the Unsorted lane.
* **Why a hybrid:** rules are free, instant, explainable and work without a key; the model adds nuance and drafting. Disagreement between them is a useful uncertainty signal.

# 8. UI and design decisions

**Direction:** quiet, photo-led, minimal. Mist-white paper, one deep "canopy" green for actions, ink text, and a cherry red used only for alerts. Left-aligned serif headlines against a plain sans for forms. Nothing on screen lacks a purpose: no carousels, no badges that are not information. Photography carries the experience.

| Screen | Decision and why |
|-------|----------------------------------------------|
| **Home** | Full-bleed ridge photograph with one line of copy; the date/guest search bar sits on the image edge so the first action is obvious. Results below are large photo cards with total price including GST, so the guest never meets a surprise at checkout. |
| **Room page** | Gallery, facts, and a sticky booking panel. The calendar shows a nightly price or "2 left" on each day, crosses out unavailable nights, and only lets a sold-out day serve as check-out. Rate plans show the **total** per plan. |
| **Booking (3 steps)** | Stay → Guest → Payment, as the brief allows at most three. A persistent summary shows the live total with GST lines. Promo and test-card hints are inline. The consent notice and the "passport details are taken at check-in" note are on the guest step. |
| **Confirmation / lookup** | Large reference, full price breakdown. Lookup needs reference **and** email. |
| **Events form** | Structured: type, guests, flexible month or exact dates, nights, rooms, budget in lakh. This data fixes the category with full confidence and feeds the draft. |
| **Rates & allotment** | A 14-day grid per room type showing rate and sold/allotment; full nights tinted, blackouts hatched; click a cell to prefill a bulk-edit form with weekday chips. |
| **Enquiry inbox** | Lane tabs with counts (Unsorted highlighted when non-empty), list, and detail pane: original message, an "AI reading" card (category, confidence bar, extracted fields, warnings), one-click lane control, owner select, editable draft, history. On a phone the list and detail are separate views. |

States: every data screen has a skeleton while loading, an empty state that says what to do, and an error state with Retry. Forms show field-level errors, server validation errors map to the same fields, and the offline case has its own message. Focus rings, labels, `aria-live` price updates and `prefers-reduced-motion` are respected. Layouts are responsive down to a phone (calendar collapses to one month, tables scroll inside their own container).

# 9. Security, privacy and compliance

* **No secrets in the repo.** `.env` ignored; `.env.example` has names only; the app refuses to start without a strong `JWT_SECRET`.
* **Validated inputs.** Every endpoint validates with zod (types, ranges, formats, unknown fields stripped). Mongo operators cannot be injected because typed fields reject objects. Regexes built from user text are escaped.
* **Access control.** Roles enforced on the server (`requireRole`), not just hidden in the UI: staff-only admin and inbox, rates/promos/bookings limited to reservations and GM. Public sign-up cannot create staff. Booking lookup requires code and email. Guest views omit payment references.
* **Abuse and transport.** helmet with CSP, rate limits on login, booking, lookup and public enquiries, 50 KB body limit, Secure/httpOnly/SameSite cookies in production, bcrypt, constant-time compare on the ingest key.
* **Payments.** Mock gateway; card numbers and CVC are never stored or logged, only the last four digits.
* **CSV export** neutralises spreadsheet formula injection.
* **DPDP Act 2023.** Explicit consent checkbox on booking and event forms (timestamp stored); purpose-limited fields; passport/Form C data deliberately not collected online; logs carry no request bodies. Not built: data-erasure request flow and a retention job (see section 11).

# 10. Testing

`npm test` runs 28 unit tests with Node's built-in runner and no database: the concurrency and rollback tests above; GST slab boundaries, plans, promos and multi-room totals; date validation (past, impossible dates, horizon, IST rollover); mock-gateway success, declines and bad input; CSV quoting and injection; the three sample enquiries, vague and complaint messages, Indian date and budget formats; LLM valid, malformed, failing, contradicting and bad-date cases; the price detector and draft guard; and owner assignment.

**Honest gap:** the environment where this was built had no MongoDB, so the HTTP routes and the seed script were syntax-checked and the app was load-tested, but not exercised against a live database; the atomic update is tested through a faithful in-memory model rather than real Mongo. The first thing to run on a machine with Mongo is `npm run seed` and the review path in deployment.md. Adding API integration tests with `mongodb-memory-server` is the first next step.

# 11. What I cut, and what I would do next

**Cut (deliberately):** real payment gateway and webhooks; real email/WhatsApp delivery and inbound parsing (the ingest endpoint is the seam where they plug in); refunds and guest self-cancellation; multi-room-type baskets; calendar-based event availability and event pricing; the reservation-system integration beyond the CSV; automated GM escalation if a complaint is unread; photo CMS.

**Next:** (1) integration tests against Mongo and an end-to-end browser test of the booking flow; (2) real gateway (Razorpay) with webhook-confirmed payment and a short stock hold with expiry; (3) WhatsApp Business and email-forwarding adapters; (4) first-reply SLA timer and breach alerts by working hours; (5) DPDP data-erasure and retention jobs, plus an audit log of staff views of guest data; (6) price/allotment change audit trail and rate-plan restrictions (minimum stay); (7) event proposals with their own pricing; (8) real photography as AVIF/WebP with `srcset`; (9) measuring direct share and reply time on a dashboard against the 20% and 30-minute targets.

**Known limits:** one active physical inventory per room type (no room numbers); the rules engine is English-only (Hindi/Kannada messages go to Unsorted by design); GST needs professional sign-off (A3).
